# Prompt 1 · 需求点拆解

> 输入：**素材清点产出 `asset-inventory.json`（必选）** + 需求正文 + （可选）业务规则库。
> 产出：原子需求点清单 JSON。只做拆解，不设计用例。
>
> **前置依赖**：必须先跑 `prompts/00-asset-inventory.md`。
> `图片依据` 字段的原料（图号 / 界面名 / 引用措辞 / 提取元素）全部来自 `asset-inventory.json`
> 的 `image_refs[]` 与 `image_elements[]`，**逐条搬运，不要重新看图、不要压缩**。

```text
【输入·素材清点】
{{粘贴 asset-inventory.json 的 image_refs 与 image_elements 两段}}

【输入·需求正文】
{{粘贴需求文档 / 用户故事 / 接口说明}}

【输入·业务规则】
{{粘贴业务规则或制度原文；若没有，只依据需求原文与素材清点，不得推断}}

【任务】把需求素材拆解为原子需求点。只做拆解，不设计用例。

【约束】
1. 一个需求点只承载一条独立业务规则，必须能被单独验证；
2. 依据分两类，分别填写，不得混写：
   - 「文本依据」：引用需求正文原句；
   - 「图片依据」：数组，每项含 图号 / 界面名 / 引用措辞 / 提取元素；
     图号必须来自 asset-inventory.json 的 image_refs，提取元素逐条搬运 image_elements；
3. 两类依据至少一个非空；都为空即视为编造，直接不合格；
4. 「纯图需求点」（正文只有『如图所示』这类无信息量的措辞）：
   文本依据填 ""，待确认可保持 false（图本身就是需求源），
   但验收标准必须写明「依据图 img-N 的 X 元素」；
5. 图里有、正文完全没提的元素（尤其按钮、状态取值、查询条件、分页上限），
   必须单独成需求点，文本依据填 ""，标注「图片新增」——这是漏需求高发区；
6. 正文与图片矛盾时，拆为两条需求点，均标 待确认: true，不得替业务方取舍；
7. 严禁编造业务规则；规则不确定时列入「待确认项」清单；
8. 覆盖以下七类需求，缺哪类要显式说明：功能、规则、流程、状态、数据、权限、异常。

【输出】严格 JSON，不要额外解释：
[{
  "id": "R1",
  "需求点": "一句话描述这条规则",
  "类型": "功能|规则|流程|状态|数据|权限|异常",
  "文本依据": "需求正文中的原句；无则填 \"\"",
  "图片依据": [
    {
      "图号": "img-2",
      "界面名": "新增英文研报",
      "引用措辞": "b. 字段如图所示",
      "提取元素": [
        "字段：标题*（文本输入，必输）",
        "按钮：直接上架（弹窗底部，主按钮）"
      ]
    }
  ],
  "业务规则": "可判定的规则表述，含具体阈值/枚举值",
  "验收标准": "满足什么条件算通过，必须唯一可判定",
  "待确认": false
}]
```

## 失败信号

- 拆出的需求点无法单独验证 → 合并了多条规则，重新拆。
- 出现"等等/其他/相关"这类兜底描述 → 拆解未完成。
- `文本依据` 与 `图片依据` 同时为空 → 模型在编造，检查输入是否缺素材清点结果。
- 正文有「如图所示」类措辞，但对应需求点的 `图片依据` 为 `[]` → 锚点未落到位，打回第 0 步。
- `提取元素` 只有 1 条，或写成「界面上有若干按钮」→ 摘要有损，回第 0 步重提。
- 图里明显有按钮/状态取值/查询条件，但没有任何需求点引用该图 → 漏需求，打回。
- 正文与图矛盾却只保留了一条需求点 → 替业务方拍板，打回。

## 图片依据的质量要求（质检口径）

| 检查项 | 合格 | 不合格 |
|---|---|---|
| 图号有效性 | `img-2`，存在于 manifest.json | `图2`、`新增界面截图`、空 |
| 提取元素粒度 | 逐条罗列，保留原文用词 | 「若干字段和按钮」 |
| 覆盖度 | 图里属于八类的元素都出现在某个需求点里 | 只提了字段，按钮/状态全丢 |
| 纯图需求点 | 验收标准写明「依据图 img-N 的 X 元素」 | 验收标准写「按图实现」 |
